# Claim-to-Evidence Validation (AIS 2.1)

## 1. Overview and Core Purpose

A critical vulnerability in LLM-assisted SOC workflows is **reasoning hallucination**: generating logically coherent arguments built upon non-existent artifacts, inaccurate byte quantities, or inverted flow directions.

The **Verdict Claim Validator** (`backend/app/services/verdict_claim_validator.py`) inspects the natural language reasoning generated by the model, extracts every factual claim and entity reference, and mechanically verifies them against canonical incident telemetry.

---

## 3. Entity Resolution Mechanics

### IP Address Grounding
- Uses strict IPv4 (`\b(?:\d{1,3}\.){3}\d{1,3}\b`) and IPv6 pattern extractors.
- For every IP cited in the reasoning, searches `src_ip`, `dest_ip`, `source_ip`, `destination_ip`, `client_ip`, and raw event logs.
- If an IP appears in the reasoning but exists nowhere in the incident telemetry, it is flagged as an **unsupported entity**, setting `unsupported_claims_count > 0` and triggering Guardrail G2.

### Numeric Quantity & Unit Verification
- Extracts byte counts, packet volumes, and port numbers.
- Accounts for unit scaling (e.g., model stating "approximately 2.13 GB" when telemetry contains `sentBytes64: 2130499380`).
- Flags discrepancies where the model claims substantial transfers when telemetry reports zero or negligible bytes.

---

## 4. Directional Contradiction Detection

Directional inversion is a common source of false escalations and missed exfiltrations. The validator checks:

1. **Explicit Flow Headers**: If telemetry specifies `"flow_direction": "inbound"` or `"direction": "ingress"`, but model reasoning states `"outbound exfiltration observed"`.
2. **Port-Based Inferences**: If well-known internal services receive connections from external endpoints, asserting that internal data was "sent out" without proof of egress byte flow is flagged as a directional contradiction.
3. **Byte Asymmetry**: In exfiltration alerts, if `rcvBytes` is large but `sentBytes` is trivial, any claim of massive outbound data movement is flagged as a severe contradiction.

---

## 5. The Critical Reference Case: `PH_RULE_LARGE_OUTBOUND_XFER`

### The Metadata Trap
In FortiSIEM incident telemetry, the rule `PH_RULE_LARGE_OUTBOUND_XFER` frequently includes:
```json
{
  "sentBytes64": 2130499380
}
```

Unconstrained LLMs frequently fall into one of two hallucinations:
1. **The Phantom Threshold Fallacy**: The model hallucinates that `2,130,499,380 bytes` (approx. 2 GB) is the *configured rule threshold*, asserting that any transfer below 2.13 GB is therefore benign.
2. **The Assumed Ingress Fallacy**: The model fails to verify whether `sentBytes64` represents outbound or inbound traffic relative to the protected enterprise boundary.

### The Defensive Validation Guard
`VerdictClaimValidator` implements explicit regex checks for threshold assertions:
```python
THRESHOLD_PATTERNS = [
    r"configured\s+(?:threshold|limit)\s+(?:of\s+)?(\d+[\w\s]*)",
    r"rule\s+threshold\s+(?:is|was)\s+(\d+[\w\s]*)",
    r"baseline\s+(?:threshold|limit)\s+(?:of\s+)?(\d+[\w\s]*)"
]
```
If the model cites `2130499380` as an established rule threshold without authoritative SIEM configuration metadata proving this threshold, the validator:
- Marks the claim as an **Unsupported Threshold Assertion**.
- Penalizes the claim support score by 40 points.
- Triggers **Guardrail G5**, automatically forcing the verdict to `REQUIRES_ANALYST_ATTENTION`.
