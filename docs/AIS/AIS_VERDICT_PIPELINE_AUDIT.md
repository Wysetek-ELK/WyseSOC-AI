# AIS 2.0 AI Verdict & Simulation Execution Pipeline Audit

**Scope:** Step-by-step verification of the 12-stage AI Verdict & Simulation lifecycle across:
1. **AIS G8 Policy Simulation** (`POST /api/prompts/rule/{id}/evaluate-simulation` -> `PolicySimulationService`)
2. **AI Triage Workbench / Live Triage** (`POST /api/incidents/{id}/ai-verdict`, worker & scheduler -> `VerdictTriageAgent`)
3. **Legacy Dry-Run Lab** (`POST /api/dry-run/*` -> `ValidationEngine`)

## 2. Critical Execution Findings

### A. Does AIS Gate G8 Execute Real Inference or Only Read Stored Results? (`AIS-F02`)
**Both stages happen in sequence, and BOTH are separated:**
1. Clicking **Run Simulation** (`frontend/src/app/agent-intelligence-studio/page.tsx:681-697`) calls `POST /api/prompts/rule/{id}/evaluate-simulation` -> `PolicySimulationService.evaluate_candidate_policy`. That executes a **fresh synchronous run** of `run_dry_run_intelligence_evaluation(..., sample_limit=50)` using the **default hardcoded `provider_type="SIMULATED"`** (`policy_simulation_service.py:199, 1084`) and persists `HistoricalEvaluationRunRecord` + `HistoricalEvaluationResultRecord`. **No LLM call occurs.**
2. Next, Studio calls `POST /api/prompts/rule/{id}/validate-quality` (`prompts.py:480` -> `_compute_policy_quality_readonly` at `:405-453`), which **only queries the stored `HistoricalEvaluationRunRecord`** matching `policy_version_id == str(target_ver.id)` and validates `policy_digest` freshness (`policy_quality_validator.py:691-696`). Notice `verdict-intelligence/page.tsx:159-163` ALSO hardcodes `provider_type: "SIMULATED"` and omits `rule_id`/`policy_version_id`!

### B. Zero Ground-Truth Data Leakage Verification
- **Strict sanitization confirmed:** Both `build_model_facing_payload` (`model_payload_allowlist.py:5-30, 92-175`) and `HistoricalGroundTruthValidator.sanitize_incident_for_inference` (`historical_ground_truth_validator.py:39-78`) recursively strip resolution notes, analyst comments, `cleared*`, `isMlGenerated`, and `mttr` before model/simulator execution. Live incidents additionally expose a `/api/incidents/{id}/model-payload` audit inspection endpoint (`incidents.py:94-130`).

### C. `NETWORK_SCAN` Telemetry Field Mapping Blind Spot (`AIS-F10`)
- `DetectionArchetypeRegistry` (`detection_archetype_registry.py:119-124`) declares `NETWORK_SCAN` `mandatory_core_fields = ["security.event_type", "event.timestamp", "network.source_ip", "network.destination_port"]`, and `EvidenceRequirementMapper` sets `critical=True` on all four.
- `EvidenceNormalizationService.FIELD_MAPPINGS` (`evidence_normalization_service.py:58-59`) maps `"destport"` and `"dest_port"`, but **omits `"destination port"`, `"destination_port"`, `"destinationport"`, `"dstport"`, `"dst_port"`** — and the fallback heuristic at `line 303` (`"ip"`, `"host"`, `"domain"`, `"user"`, `"file"`, `"path"`, `"hash"`, `"proc"`) omits `"port"`. Meanwhile, `EvidenceSufficiencyEngine._match_field` (`evidence_sufficiency_engine.py:165-190`) has **no `network.destination_port` alias**. Thus valid FortiSIEM port-scan attributes like `"Destination Port"` or `"dstPort"` are dropped during normalization and trigger false `INSUFFICIENT` abstentions.
- Additionally, `EvidenceNormalizationService` (`lines 241-249`) checks `raw.get("event") or raw.get("events") or raw.get("attributes")`; if any of those keys is truthy alongside `rawEvents`, `rawEvents` is never extracted in Section 3.

### D. Fragmented Validation Engines (`AIS-F11`)
Notice the codebase retains an independent **Legacy Dry-Run Lab** (`api/dry_run.py` + `dry_run_service.py` `ValidationEngine` -> `DryRunJob`/`DryRunResult` -> `RuleMaturityService` in `maturity_service.py`), using `PolicyCompilerService` + `TokenBudgetService` and configurable `provider_type` (`SIMULATED` or `OPENAI_COMPATIBLE`), completely disconnected from AIS G8 (`historical_evaluation_runs`) and `VerdictTriageAgent`!
