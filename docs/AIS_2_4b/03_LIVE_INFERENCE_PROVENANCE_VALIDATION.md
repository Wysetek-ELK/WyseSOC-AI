## 1. Executive Summary

This document establishes and audits the strict, mutually exclusive execution provenance taxonomy in Verdictum AI. 

To eliminate any ambiguity between genuine physical GPU inference and offline test simulations, the platform enforces four distinct execution classifications:

$$\text{Execution Taxonomy} \in \{\text{LIVE\_PROVIDER}, \text{OFFLINE\_SIMULATION}, \text{PREFLIGHT\_ABSTENTION}, \text{PROVIDER\_FAILURE}\}$$

Under no circumstances may a test or benchmark report claim live GPU acceptance unless genuine HTTP request-response evidence is obtained from the deployed model endpoint.

## 3. Forensic Provenance Audit Fields

Every individual incident execution produces a `BenchmarkIncidentResult` containing the complete forensic execution chain:

1. `evaluation_run_id`: Unique identifier for the benchmark execution run (e.g. `PILOT-AIS-2.4b`).
2. `incident_id`: FortiSIEM numerical incident identifier.
3. `model_name`: Verified model identifier string (`Qwen/Qwen2.5-7B-Instruct-AWQ`).
4. `provider_name`: Dispatched provider class (`OpenAICompatibleProvider`).
5. `execution_git_sha`: The exact Git commit SHA active during execution (`git rev-parse HEAD`).
6. `policy_version`: Approved prompt compiler policy version number.
7. `prompt_hash`: SHA-256 hash of the complete compiled system prompt and delimiter payload.
8. `executed_at_utc`: ISO 8601 UTC timestamp of execution.
9. `endpoint_identity`: Sanitized endpoint host/port (e.g. `http://172.26.41.241:8000/v1`), with any embedded basic-auth credentials strictly redacted (`//***@`).
10. `raw_model_response_id`: Unique provider response ID or capture ID from database.
11. `requested_max_tokens`: Exact integer passed in request `max_tokens` field (strictly $\ge 768$).
12. `prompt_tokens`: Actual tokens reported on wire by provider (or `None`).
13. `completion_tokens`: Actual completion tokens reported on wire by provider (or `None`).
14. `total_tokens`: Actual total tokens reported on wire by provider (or `None`).
15. `finish_reason`: Provider-reported finish reason (`stop`, `length`, `provider_error`, `abstained_preflight`).
16. `latency_ms`: Measured HTTP round-trip latency in milliseconds.
17. `raw_proposed_verdict`: Exact proposal returned by model (`TRUE_POSITIVE`, `FALSE_POSITIVE`, `REQUIRES_ATTENTION`, or `None`).
18. `raw_proposed_confidence`: Raw model confidence percentage.
19. `schema_compliant`: Boolean indicating whether model JSON conformed to target schema.
20. `final_authoritative_verdict`: Authoritative verdict produced by `IndependentVerdictValidator`.
21. `validation_reason_codes`: Authoritative reason codes explaining validator disposition.

## 4. Separation of Wire Usage vs Local Tokenizer Estimates

The platform strictly maintains two separate token accounting channels:
- **Preflight Estimation Channel (`ModelTokenizerService`):** Uses model-specific Qwen BPE tokenization to pre-calculate section allocations and determine compaction eligibility prior to wire transmission.
- **Authoritative Provider Wire Usage Channel (`OpenAICompatibleProvider`):** Extracts exact `usage.prompt_tokens` and `usage.completion_tokens` returned by the vLLM engine over HTTP.

If the model endpoint does not return usage metadata, or if the request fails, the wire token fields are preserved as `None`. They are never manufactured from preflight estimates.
