## 2. Comprehensive Root Cause Investigation Across Ten Areas

### 2.1 Question 1: Why all 20 benchmark records recorded `execution_provenance = OFFLINE_SIMULATION`
- **Code Finding:** In `empirical_benchmark_harness.py::evaluate_single_incident`, execution mode branches on `if is_live and model_endpoint:`. In `scratch/run_stage6_benchmark.py`, the runner explicitly invoked `mode="offline"`.
- **Runtime Finding:** Because `mode="offline"` was specified, line 958 invoked `cls._simulate_model_proposal_offline(incident_rec, norm_result)`. No live HTTP socket was opened to any model provider endpoint. The provenance string was faithfully assigned `"OFFLINE_SIMULATION"` by line 1078.

### 2.2 Question 2: Why `is_live_measurement = false`, and latency, token usage, and finish reasons are null
- **Code Finding:** In `evaluate_single_incident` under `mode="offline"`, lines 964-969 explicitly set:
  ```python
  elapsed_ms = None
  p_tokens = None
  c_tokens = None
  t_tokens = None
  finish_reason = None
  requested_max_tokens = None
  ```
- **Runtime Finding:** Since no network request occurred, no network round-trip time existed, no server response headers were parsed, and no provider finish reasons (`stop` or `length`) were emitted.

### 2.3 Question 3: How the five pilot proposals were generated and whether any actual vLLM API calls occurred
- **Code Finding:** In `scratch/run_stage5_pilot.py`, lines 183-189 called:
  ```python
  simulated_proposal = EmpiricalBenchmarkHarness._simulate_model_proposal_offline(mock_rec, norm_result)
  ```
- **Runtime Finding:** **Zero vLLM API calls occurred during Stage 5.** The pilot script computed wire token limits using the local tokenizer service and then evaluated the proposals generated by the offline heuristic function.

### 2.4 Question 4: Why CrowdStrike results show exactly 85% confidence and Prisma SASE show 88%
- **Code Finding:** In `empirical_benchmark_harness.py::_simulate_model_proposal_offline`:
  - Lines 751-754 hardcode Prisma SASE proposals:
    ```python
    return {
        "verdict": "TRUE_POSITIVE",
        "confidence": 88.0,
        ...
    }
    ```
  - Lines 775-778 hardcode CrowdStrike proposals:
    ```python
    return {
        "verdict": "FALSE_POSITIVE" if has_benign_token else "TRUE_POSITIVE",
        "confidence": 85.0,
        ...
    }
    ```
- **Runtime Finding:** The 88% and 85% confidence scores were static literals from the offline mock heuristic, completely decoupled from any probabilistic model sampling.

### 2.5 Question 5: Why a VERIFIED_FP incident (`132499009`) received an accepted TRUE_POSITIVE
- **Telemetry Finding:** In `incidentId_132499009.json`, the telemetry records an alert on `File Name: ss-widget.min.js`, `Application Name: surveysensum-base`, `Application Category: business-and-economy`, `VendorSeverity: Low`, downloading from `108.159.61.117` (Amazon CloudFront) over HTTPS. The analyst closed it with `Resolution: False Positive` and `ClearedReason: No suspicious activity was identified during the analysis`.
- **Defect Mechanism:**
  1. `_simulate_model_proposal_offline` blindly emitted `TRUE_POSITIVE` citing `file.name` and `network.source_ip`.
  2. In `IndependentVerdictValidator.validate_verdict` (lines 302-315), the validator checked whether any grounded claim represented *"grounded security tradecraft"*.
  3. While `process.name` and `file.name` were excluded in `identifier_fields`, `network.source_ip` was NOT excluded. Because `network.source_ip` (`172.25.14.80`) was grounded, the validator treated a standard local IP address as proof of *"security tradecraft"*, accepting `TRUE_POSITIVE` without requiring affirmative attack evidence.

### 2.6 Question 6: Why the benchmark is described as deduplicated despite duplicate incident clusters
- **Code Finding:** `load_dataset_unified` only deduplicated by primary key (`incident_id`).
- **Data Finding:** Several incidents in the 20-incident corpus are batch closures of identical events:
  - `132599145`, `132599146`, `132599330` share the exact identical `cleared_reason` (*"Case has been raised for the similar incidents."*) and timestamp.
  - `132438483` and `132439932` share the exact identical `cleared_reason` (*"kill process is true"*).
- **Audit Conclusion:** Reporting metrics solely on the 20 individual IDs without distinct unique-cluster metrics artificially inflated sample size and created duplicate statistical dependence.

### 2.7 Question 7: Whether verified TP labels are based on completed investigations or merely escalation tickets
- **Audit Finding:** In `fixtures/Incident json.zip`:
  - `132596403`: `cleared_reason = "Mail has been sent already"`
  - `132599145`, `132599146`, `132599330`: `cleared_reason = "Case has been raised for the similar incidents."`
  - `132502453`: `cleared_reason = "Informed to client, alert still generating"`
- **Conclusion:** These notes represent operational notification and escalation actions, not completed forensic confirmations of compromise. Under `strict_forensic_only = True` (`historical_ground_truth_validator.py`), these MUST be classified as `UNVERIFIED`.

### 2.8 Question 8: Whether the test environment uses SQLite while Server 1 uses PostgreSQL
- **Code Finding:** In `backend/app/config.py`:
  - Default `DATABASE_URL` is `sqlite+aiosqlite:///backend/ai_verdict.db`.
- **Deployment Finding:** In `deployment/env.production.example` (lines 29-31):
  - Server 1 production is configured for PostgreSQL:
    `DATABASE_URL="postgresql+asyncpg://aiverdict_user:...@127.0.0.1:5432/ai_verdict"`.
- **Conclusion:** Local evaluations run on SQLite, while Server 1 production runs PostgreSQL.

### 2.9 Question 9: Whether 8,192-token capacity was actually enabled on Server 2 or only calculated offline
- **Audit Finding:** In AIS 2.4, UPLA Gate 2 (Remote Deployment) was explicitly **DECLINED** by the operator.
- **Runtime Fact:** Server 2 was never accessed, and vLLM was never restarted with `--max-model-len 8192`. The 8,192 capacity was calculated mathematically from GQA formulas and tested with the local tokenizer service. **Server 2 remains on its prior active runtime configuration.**

### 2.10 Question 10: Why the three original Prisma incidents now fit within the 4,096-token prompt budget
- **Code Finding:** In AIS 2.3b, the payload passed full raw event logs (often >2.5 KB per event with uncompacted syslog headers), resulting in >6,200 prompt tokens.
- **Runtime Finding:** In AIS 2.4, `TokenBudgetService` and `EvidenceNormalizationService` extracted and formatted only the normalized `canonical_evidence` records (~15 key-value pairs). Without the megabyte-scale raw syslog bloat, the prompt fit comfortably within ~3,110 tokens even under the 4,096 ceiling.
